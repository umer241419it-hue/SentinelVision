# Inference Provenance — Cryptographic Coverage & Limitations (Stage 5)

## 1. What Part A (Inference Sealing) Actually Binds and Proves

Part A implements an immutable cryptographic seal around every prediction executed through `inference-provenance/src/wrapper.py` (`sealed_predict`).

### Specifically Bound Elements:
- **`sealID`**: Unique seal identifier (`seal-<uuid4>`) identifying this specific inference instance.
- **`modelAssetID`**: Identifier of the model asset (e.g. `model-id-00000028`).
- **`inputHash`**: SHA-256 digest computed across contiguous raw input tensor bytes.
- **`modelDigest`**: SHA-256 file digest of the exact model weights file (`model.pt`) used during inference.
- **`config`**: Preprocessing metadata and execution parameters (channel order, resolution, normalization, live-detected device).
- **`nonce`**: Cryptographic random hex string (16 bytes / 32 hex chars) ensuring per-inference uniqueness.
- **`timestamp`**: UTC ISO-8601 timestamp generated at inference execution time.
- **`outputSummary`**: Structured model inference results (predicted class, confidence score, and output probability distribution).
- **`signerModule`**: Name of the module identity authority (`"InferenceProvenance"`).
- **`contentHash`**: SHA-256 digest computed over the RFC-8785 canonical JSON serialization of the 9 preceding fields.
- **`signature`**: 64-byte (128 hex chars) Ed25519 signature computed over `contentHash` using the registered `InferenceProvenance` module private key.

### What Part A Proves:
1. **Execution Authenticity**: Proves that an inference execution producing `outputSummary` was executed using the exact model weights identified by `modelDigest` on the exact input array identified by `inputHash` under the specified `config`.
2. **Post-Execution Non-Repudiation**: Any subsequent modification to any of the 9 signed fields (input, output, model digest, config, nonce, timestamp) invalidates `contentHash` and fails `verify_seal()` / `verify_fields()`.

---

## 2. What Part A Does NOT Prove (Explicit Honest Reporting)

- **Does NOT verify model trustworthiness**: Part A does not detect backdoors, trojans, or weight tampering in the model itself. A poisoned or backdoored model will produce a perfectly valid, signed seal binding its backdoored inference. Model security verification is strictly the responsibility of **Stage 4 (Model Integrity)**.
- **Does NOT verify input pedigree before hashing**: Part A cannot prove that the input image or tensor was not manipulated, spoofed, or adversarial *prior* to reaching the `sealed_predict()` wrapper. This is a "garbage-in, garbage-out" cryptographic binding guarantee: it binds whatever was fed into the model, but does not certify the raw sensory provenance before hashing.

---

## 3. What Part B & Chaincode Replay Guard Actually Prove

Part B retrofits the Hyperledger Fabric ledger pipeline so that every finding submitted by a module must be signed across its 8 core fields (`assetID`, `moduleName`, `reason`, `evidenceHash`, `confidence`, `severity`, `disposition`, `timestamp`) with that module's Ed25519 identity key, storing the signature as the 9th field. Additionally, chaincode v1.3 enforces duplicate-evidence rejection.

### What Is Proven:
1. **Read-Time Tamper Detection**: Any direct, out-of-band modification to world state in CouchDB (such as manually modifying `disposition` from `"ACCEPT"` to `"QUARANTINE"`) is caught instantly on the very next `GET /findings/:id` read request.
2. **Zero-Write Verification**: Detection requires **no intervening chaincode write transaction** or peer endorsement consensus; tampering is flagged immediately at read time (`signatureStatus: "TAMPERED"`).
3. **Module Origin Authentication**: Authenticates that the finding payload was generated by the legitimate module identity holding the registered private key.
4. **Replay Protection Scope**: The chaincode rejects any finding whose evidenceHash has already been committed under any assetID, which prevents replay of byte-identical evidence. This does NOT constitute session-level nonce/timestamp freshness checking — a sealed record's nonce and timestamp are bound into its signature for integrity, not independently validated for recency.

---

## 4. What Is NOT Covered (Legacy Data Limitations)

- **Legacy Findings (`UNSIGNED_LEGACY`)**: Findings committed prior to the Stage 5 Part B upgrade (under chaincode sequence 1, version 1.0) contain only 8 fields and have no cryptographic signature.
  - While they are protected by Fabric's multi-organization endorsement policy at transaction commit time, they have **no read-time cryptographic tamper-detection guarantee**.
  - If a legacy finding is tampered in CouchDB, the bridge's `GET /findings/:id` can only report `signatureStatus: "UNSIGNED_LEGACY"` and cannot detect content alterations on read.
